> 版本：V2.0｜更新日期：2026-10-19｜需求基线：V4.2  
> **使用方式：从第 0 阶段向下实施；每阶段未通过验收不得标为已完成。**  
> 状态含义：✅ 已提交代码（不代表运行通过）；🟡 已设计/待实现；🔬 待 Demo 验证；⛔ 本项目明确不做。

## 0. 项目目标、边界与当前进度

### 0.1 产品目标

- **EA 源账户**：自研 MQL5 EA，运行在 MT5 Netting 主账户；支持一账户多 EA、每 EA 独立账户及混合使用。
- **跟单账户**：MT4 与 MT5 Hedging；一个跟单账户可订阅多个策略。
- **跟单路线**：Broker 已确认成交 + EA 独立虚拟仓位 → CopyFactory External Signals → 跟单账户。**仍待真实 Demo 端到端验证。**
- **明确排除**：⛔ MT5 Netting 主账户作为标准 CopyFactory Provider 直接跟单；⛔ MT4 EA；⛔ 首期自建跟单执行引擎；⛔ 未测试即接入实盘。
- **其他核心业务**：账户生命周期维护、Broker/Server 实时搜索、账户品种/规格/默认品种、行情、订单与持仓、独立手动交易、EA Bridge、WebSocket、审计/风控、Web 运营后台。

### 0.3 开发环境和统一规范

开发环境：macOS、Node.js 24、pnpm、PostgreSQL 17 与 Redis 均在本机，**不使用 Docker Compose**。后端 NestJS + TypeScript，Prisma 7；Web Vue 3 + Vben Admin 5；计划使用 BullMQ 和 MetaAPI 官方 SDK。MQL5 通过 MT5/MetaEditor 调试。

**中文规范**：README、Markdown、代码注释、Swagger、业务错误和验收记录用简体中文；TypeScript/数据库/API 标识符、第三方 SDK 名和交易枚举保持英文。

### 0.4 模块总体关系

```text
Web（Vben Admin） -- REST/WebSocket --> NestJS API
                                         |
                            PostgreSQL + Redis/BullMQ
                                         |
                +------------------------+---------------------+
                |                                              |
   账户与手动交易模块                                  EA Bridge / 信号模块
                |                                              |
        MetaAPI Worker（Broker 事实） <--- MT5 Netting EA 交易意图
                |                                              |
                +-------------- Deal 核验 ---------------------+
                                         |
                            Netting EA 虚拟仓位账本
                                         |
                         CopyFactory External Signals
                                         |
                            MT4 / MT5 Hedging 跟单
```

**交易通道严格分离**：EA 自动跟单使用 External Signals；Web 手动交易使用独立 TradeModule → MetaAPI RPC → Broker；手动交易不自动生成跟单信号。

## 第 2 阶段：账户生命周期 + Broker/Server 搜索

**状态：🟡 待开发。** **依赖：第 1 阶段。**

**怎么实现**
1. 建立 AccountModule、MetaApiProvisioningAdapter、BrokerServerModule 和账户 DTO。所有第三方请求都由后端代理，MetaAPI Token 不进入前端。
2. 根据 MT4/MT5 平台搜索 Broker/Server：MetaAPI Provisioning `GET /known-mt-servers/:version/search?query=...`。前端防抖 300–500ms，按 Broker 分组下拉；由于搜索结果不完整，必须提供**手动 Server 输入**。
3. 区分远端“注册已有 Broker 登录到 MetaAPI”、远端 `deploy`、Broker 连接状态、SDK Streaming 同步状态、本地停用和本地解绑。不要把添加 MetaAPI Account ID 误称为新建 Broker 账户。
4. 使用 `getAccount` 等接口读取 platform/login/server/currency/accountState/connectionStatus；与 Broker 实际账户信息核验。账户接入、部署和解绑通过任务表管理；解绑前检查 EA、订阅、UNKNOWN 交易和待同步外部信号。
5. 分开存储 `localStatus`、`provisioningStatus`、`brokerConnectionStatus`、`syncStatus`、`lastObservedAt`；失败为待确认/错误，不因 API 请求成功直接显示 Broker 已连接。
6. 账户按 organizationId 做多租户授权；角色区分 EA_SOURCE、SUBSCRIBER，未来支持一个账户多角色。

**建议表**：`organizations`、`users`、`organization_members`、`trading_accounts`、`account_roles`、`account_lifecycle_jobs`、`account_snapshots`。

**计划 API**：`GET /brokers/servers?platform=MT5&query=...`；`GET/POST /accounts`；`GET /accounts/:id/status`；`POST /accounts/:id/deploy`、`/sync`、`/disable`、`/unbind`。

**验收**：MT4/MT5 搜索可用，返回 Broker 分组 Server；无搜索结果可手输；重复绑定和无权账户拒绝；解绑不自动删除 MetaAPI 远端账户；账户错误、连接和时间戳真实可查。

## 第 3 阶段：账户品种、规格、默认品种与行情

**状态：🟡 待开发。** **依赖：第 2 阶段账户接入。**

**怎么实现**
1. AccountSymbolModule 在账户同步完成后按 accountId 调 MetaAPI `getSymbols()`，不是按 Server 统一套用品种；按需调用 `getSymbolSpecification(symbol)` 保存 min/max Volume、Volume Step、Digits、Tick Size、合约量、止损限制、时段等可用规格。
2. `account_symbols` 以 `(accountId, brokerSymbol)` 唯一；分开保存 Broker 可见/交易资格与平台 `isEnabled`，并设置每账户唯一的 `defaultSymbol`。**开启品种不等于修改 Broker 权限**。
3. 品种清单首次全量同步、后续周期/手动刷新；删除/不可见品种保留历史并标记不可用，数据有 `lastSeenAt`、`specificationUpdatedAt`。
4. MarketDataModule 通过 MetaAPI Streaming 聚合账户+品种报价订阅，缓存 bid/ask、报价和接收时间；前端展示实时/STALE，不为每个 Web 连接另开上游 MetaAPI 订阅。
5. 交易时校验 Broker 可用、市场/报价新鲜度、手数步长、交易时段、止损距离、平台启用状态，并以 Broker 最终返回为准。
6. 建立 `account_symbol_mappings`，明确源 EA 原始品种到 MT4/MT5 Subscriber 品种的映射，如 XAUUSD → XAUUSDm，禁止只按名称猜测。

**建议表**：`account_symbols`、`account_symbol_mappings`、按需 `symbol_specification_history`；高频行情先缓存，不直接逐 Tick 写业务数据库。

**计划 API**：`GET/POST /accounts/:id/symbols[/sync]`、`PATCH /accounts/:id/symbols/:symbol`、`PUT /accounts/:id/default-symbol`、`GET /accounts/:id/symbols/:symbol/specification`、`GET /accounts/:id/quotes/:symbol`。

**验收**：不同账户的实际品种/规格独立；启用/停用、唯一默认品种正确；不存在的 Broker 品种无法新下单；后缀差异只能通过显式映射；过期行情不显示为实时。

## 第 4 阶段：MetaAPI 长连接同步、历史补拉与 Broker 成交落库

**状态：✅ 只读查询草案；🟡 持久化与同步 Worker 待开发。** **依赖：第 2–3 阶段。**

**怎么实现**
1. 重构 MetaApiReadService：按账户复用 SDK、`getRPCConnection()` / `getStreamingConnection()`，连接 `connect()` 并 `waitSynchronized()`；建立 MetaApiWorker，避免每次 HTTP 请求短连。
2. 按账户同步余额、净值、订单、仓位、历史订单与 Deal；区分 MT4 Order 和 MT5 Order/Deal/Position；MT5 Netting 不允许从账户净仓位直接推断 EA 独立仓位。
3. `broker_deals` 约束 `(accountId, brokerDealId)` 唯一；`broker_orders` 与 `broker_positions` 保存原始可追溯数据和 UTC 时间，交易数值使用 Decimal。
4. `sync_cursors` 保存成功时间与区间。断线、重启后以重叠窗口回查历史、分页/限流、幂等 Upsert，直到数据一致。同步未完成和数据超期时显示 SYNCING/STALE。
5. 事实数据与 `outbox_events` 在同一事务写入，后续通知实时模块；不能只靠 WebSocket 事件确保不丢。
6. 已有 `attribution-preview` 和 `link-executions` 仅作 PoC 辅助；增加跨批次唯一关联和数据库证据链。

**建议表**：`broker_deals`、`broker_orders`、`broker_positions`、`sync_cursors`、`outbox_events`、`broker_sync_runs`。

**验收**：首次同步可查询真实 Demo Deal；重复补拉无重复；掉线重连/进程重启后不缺交易历史；未同步完成不会显示成功；MT4/MT5 的订单与成交语义清晰。

## 第 5 阶段：MT5 EA Bridge 与交易事件来源关联

**状态：🟡 Bridge 待开发；✅ 事件关联函数已有初稿。** **依赖：第 4 阶段。**

**怎么实现**
1. MQL5 Include/EaBridge 模块集成到自研 EA，使用 OnTimer 发送 HTTPS 心跳与命令轮询，不阻塞 OnTick；配置 WebRequest 允许列表和短超时。
2. EA 注册：一次性激活码 → 实例身份 → 后端发可撤销凭证，只存哈希；实例关联 MT5 主账户、EA 定义和 Magic/品种/生效时间。
3. 交易意图上报稳定 `sourceEventId` 和 Broker Order/Deal ID；后端与第 4 阶段真实 Broker Deal 严格关联，拒绝无证据归属、Magic 冲突和跨批次重复申领。
4. 状态分开存 `desiredState`、`reportedState`、`lastHeartbeatAt`、命令状态。PAUSED 仅禁止新开仓，继续管理已有仓位；ACK 后才可展示“已应用”。
5. MQ5 交易发送/回执的具体 ID 和部分成交行为必须经真实 Demo 验证；不能依赖 Bridge 心跳决定交易事实。

**建议表**：`ea_definitions`、`ea_instances`、`ea_magic_bindings`、`ea_bridge_credentials`、`ea_heartbeats`、`ea_bridge_commands`、`ea_execution_events`、`deal_execution_links`。

**计划 API**：`POST /bridge/register`、`/bridge/heartbeat`、`/bridge/events`；`GET /bridge/commands`；`POST /bridge/commands/:id/ack`；`GET /ea-instances`。

**验收**：MT5 EA Demo 心跳、断线、命令 ACK 正确；两个 EA/同品种/相同或不同 Magic 的来源归属冲突可识别；重复事件不重复入账；暂停不影响已有仓位管理。

## 第 6 阶段：Netting EA 虚拟仓位账本

**状态：🟡 待开发，属于关键安全模块。** **依赖：第 4–5 阶段。**

**怎么实现**
1. 为每 EA、品种、逻辑仓位建立独立账本，按已确认 Broker Deal 产生不可变变动记录，计算策略目标净仓位。
2. 设计同一 Netting 源账户中不同 EA 反向交易、抵消、部分成交、费用及利润分摊规则，记录每次分配证据和版本；不能仅用 Broker 最终净持仓或者 Magic 推导。
3. 提供账本按序重放、一致性检查、人工核验标记；若出现 AMBIGUOUS 或 Broker 与虚拟账本对不上，冻结该策略的外部信号发布。
4. 账户总净仓位、EA 逻辑仓位、已发布外部信号目标和跟单端实际仓位分别建模与展示。

**建议表**：`strategy_virtual_positions`、`virtual_position_ledger`、`ledger_reconciliation_runs`，必要时逻辑仓位分组。

**验收**：单 EA 开平仓及反手重放一致；双 EA 同品种反向交易有明确归属，失败时冻结；重复 Broker Deal 不产生二次账本记录；历史回放结果一致。

5. 保留 Broker Ticket、EA 事件、虚拟仓位变化、远端 Signal ID、Subscriber Broker 执行结果及时间。

## 第 8 阶段：CopyFactory 多订阅与独立风险配置

**状态：🟡 待开发。** **依赖：第 7 阶段通过。**

**怎么实现**
1. 创建 CopyStrategyModule、SubscriptionModule，策略关联本地 EA 实例及来源主账户；每 Subscriber 可订阅多个策略并配置倍数、风险限制、启停目标。
2. CopyFactory Subscriber 配置可能包含全部 subscriptions 数组：对每 Subscriber 串行修改、合并完整期望配置、保存版本、提交远端并回读确认；避免改策略 A 时覆盖策略 B。
3. 独立维护 `desiredEnabled`、远端是否确认及 Broker 实际跟单结果；暂停新开仓复制、停止订阅且处理原仓、紧急平仓必须分开授权和设计。
4. 对每个 Subscriber 的品种映射、Volume Step、最低手数、交易模式及账户风险进行核验。

**建议表**：`copy_subscriptions`、`copy_subscription_configs`、`copy_sync_jobs`、`copy_trade_links`。

**验收**：一个 Subscriber 同时订阅多个 EA 策略；独立修改倍率不会删除其他订阅；失败任务可恢复和审计；同策略跨 MT4/MT5 Hedging 目标账户不串单。

## 第 9 阶段：受控的手动交易 TradeModule

**状态：🟡 待开发。** **依赖：第 2–4 阶段账户、品种和 Broker 同步；安全上要求先具备对账机制。**

**怎么实现**
1. 独立业务通道：授权用户 → TradeModule → 持久化 TradeRequest → MetaAPI RPC → Broker Order/Deal 回查，不经过 EA Bridge 或 CopyFactory。
2. 支持 MT4 与 MT5 Hedging Demo 的市价开仓、挂单、撤单、修改 SL/TP、全平/部分平仓；按平台分别适配 Order/Position 模型。
3. 每次提交服务端重新核验账户权限、Broker 连接与交易规格、最新报价、Volume Step、可用保证金及风险限额。
4. 本地 `Idempotency-Key` 去重、Broker 客户端关联 ID 追踪和请求状态机（PENDING/VALIDATED/SUBMITTED/CONFIRMED/REJECTED/UNKNOWN）。**Broker 不承诺本地幂等键的 exactly-once**。
5. 运行 EA 的 MT5 Netting 主账户**默认禁止人工开仓、改仓、反手或部分平仓**，以免破坏共享净仓位和策略账本；未来若要开放需独立技术设计及审批。
6. 任何 UNKNOWN 结果必须 Broker 回查后才能重试；手动交易不自动产生跟单信号。

**建议表**：`trade_requests`、`trade_request_attempts`、`trade_execution_links`、`audit_logs`。

**计划 API**：`POST /trade-requests/market-order`、`/pending-order`、`/close-position`、`/modify-protection`、`/cancel-order`；`GET /trade-requests/:id`。

**验收**：仅 Demo 环境开放；MT4/MT5 Hedging 开仓、部分平仓、改单、撤单均可回查；重复/并发/超时不造成额外交易；EA Netting 源账户人工改仓默认拒绝；跨租户无权限。

## 第 10 阶段：实时推送、Outbox 与 WebSocket

**状态：🟡 待开发。** **依赖：第 4 阶段可靠存储；可与第 8–9 阶段并行。**

**怎么实现**
1. NestJS RealtimeModule + Gateway，前端先通过 REST 获取最新 Snapshot/version，然后订阅 WebSocket 增量事件。
2. 按租户、账户、EA、订阅资源做鉴权房间；握手鉴权、过期 token、主动退出/权限撤销都应处理，不能由客户端随意指定组织 ID。
3. Broker Deal、账户状态、EA 命令回执、信号状态、订阅修改和手动交易结果写入 PostgreSQL 后经 Outbox 推送；报价等高频消息节流，可只保留最新。
4. 事件结构：`{eventId,type,resourceId,version,occurredAt,asOf,payload}`。前端按版本去重/乱序保护，掉线重新读取快照并补拉关键事件。
5. 监测 lastHeartbeatAt、lastSynchronizedAt、quoteTime 和 lastObservedAt，过期显示 STALE，不将 WS 已连接等同数据实时。

**建议表**：`outbox_events`、`event_delivery_cursors`；Redis/BullMQ 配合后续多进程处理。

**验收**：多浏览器同步、跨组织房间阻止、掉线重连状态恢复、重复/乱序不回滚 UI；WebSocket 断线不会阻断 Broker 同步和交易状态机。

## 必须遵守的项目决策

1. 主 EA 只在 MT5 Netting；跟单端 MT4 和 MT5 Hedging。
2. 一个主账户多个 EA 与每 EA 独立主账户同时支持。
3. 绝不采用 MT5 Netting 标准 CopyFactory Provider 路线。
4. EA 意图、Broker 成交、策略虚拟仓位、CopyFactory 信号、Subscriber 执行五层分离。
5. 手动交易独立、不默认跟单；EA Netting 主账户默认不允许人工改变共享净仓位。
6. Server 搜索使用 MetaAPI 接口，必须有手动服务器输入兜底；品种按账户独立同步和启用，默认品种为平台设置。
7. 当前仓库代码尚未证明外部信号的完整交易生命周期可用；未通过 Demo 不做实盘。
8. 所有中文文档、代码注释和验收记录按本实施顺序更新。
