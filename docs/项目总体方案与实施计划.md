# nest-metaapi 项目总体方案与实施计划

> 版本：V1.0｜需求基线：V4.2｜日期：2026-10-19  
> 状态：产品范围与开发路线已确定；CopyFactory External Signals 的 Netting 跟单生命周期尚未通过 Demo 验证。
> 此文档为后续开发、数据库建模、接口设计和阶段验收的主要依据。

## 一、项目目标与范围

开发一套 NestJS 驱动的 EA 策略管理与多账户跟单平台。信号来源为自主开发的 MQ5 EA，运行于 MT5 Netting 主账户；跟单端支持 MT4 和 MT5 Hedging。可在一个主账户部署多个 EA，也可每个 EA 使用独立主账户，并允许两种模式同时存在。相同 EA 定义可跨账户部署，多个跟单账户可订阅不同策略，一个跟单账户也可订阅多个策略。

业务能力包括主账户/跟单账户管理、EA 身份与心跳、远程暂停新开仓、交易事件上报、Broker 成交核验、EA 虚拟仓位、外部信号生命周期、CopyFactory 订阅、风险控制、对账、统计与审计。

**明确排除：不将 MT5 Netting 源账户注册为标准 CopyFactory Provider。** 首选通过 EA Bridge 与 MetaAPI 获取真实可核验的交易变化，经 Netting 策略虚拟仓位引擎生成 CopyFactory External Signals。该链路必须先完成 Demo 可行性验证。当前不承诺支持 MT5 Netting 跟单端；MT5 跟单首期只支持经验证的 Hedging 账户。不开发 MT4 EA、不开发自建高频跟单执行引擎。

## 三、架构及责任边界

数据链路：

1. 自研 MT5 EA 在 Netting 主账户生成交易意图并向 Broker 下单。
2. EA Bridge 上报稳定的事件 ID、EA 实例 ID、Magic、品种、交易方向和可获取的 Order/Deal ID。
3. MetaAPI Worker 独立同步 Broker 真实订单、成交、持仓及账户状态。
4. 成交关联层按账户、Order/Deal ID、Magic、品种及时间核验 EA 事件。缺乏证据或有冲突时不自动确认。
5. Netting Signal Engine 以已确认成交驱动每个 EA 独立的逻辑持仓账本，记录加仓、减仓、平仓、反手等变化。
6. Copy Signal Worker 以稳定外部信号 ID 发布或更新 CopyFactory External Signals，并回查是否被接受。
7. CopyFactory 将信号复制到符合要求的 MT4、MT5 Hedging Subscriber；最终以跟单 Broker 实际成交/持仓为事实来源。
8. NestJS 向 Web 提供账户、策略、运行状态、订阅、风险、对账、审计及告警接口。

**权威性约定：** Broker 确认真实成交；EA Bridge 确认 EA 自身状态及意图；虚拟账本表示策略级推导状态；CopyFactory 表示远端信号/订阅状态。各层状态独立，不能互相替代。MetaAPI CONNECTED 不等于 EA RUNNING，EA 心跳也不等于交易已成交。

## 四、MT5 Netting 的核心难点

在 Netting 账户中，同品种的多个 EA 交易合并到同一个账户净持仓。例如 EA-A 买入 1 手，EA-B 卖出 0.4 手后，Broker 净仓位仅剩 0.6 手；不能直接从该净仓位推导 EA-A 与 EA-B 的各自逻辑仓位。

方案采用不可变的虚拟持仓流水，单独维护每个 EA、品种和必要的逻辑仓位 ID。必须制定跨 EA 冲抵分配规则，并处理部分成交、佣金与利润分摊、反手及订单 ID 跨事件共享等边界。不能仅凭 Magic Number 就将某笔减少净仓位的交易全部归给发起该交易的 EA。

来源匹配状态：

- CANDIDATE_ONLY：只有 Magic/品种候选，缺少 Broker 精确证据；
- UNMATCHED：提供了 Broker ID，但成交尚未出现；
- AMBIGUOUS：多个事件争夺同一成交、Magic 不符或其他冲突；
- CONFIRMED：本次来源关联获得可靠证据；**并不表示 EA 逻辑仓位已完成归属**。

无法可靠解释的净仓位变化必须冻结对应信号、告警并进入人工或自动对账，不能静默发布错误复制信号。

## 五、EA Bridge 设计

Bridge 只集成在 MT5 主账户的自研 MQ5 EA 中；跟单账户不安装 EA。首期接口为激活注册、心跳、读取控制指令、指令 ACK、上报交易事件。注册使用一次性激活码与可轮换的实例密钥；后端仅存凭证哈希，连接使用 HTTPS。

EA 定期在 OnTimer 处理短超时 WebRequest，不要阻塞 OnTick 交易逻辑。MT5 终端须将地址加入 WebRequest 允许列表；回测时用模拟 Bridge 实现。示例配置：心跳约 15 秒、命令轮询约 3–5 秒；最终按压测与网络环境调整。

暂停 RUNNING → PAUSED 的定义：只禁止新增开仓，已有仓位的止损、风控、管理和平仓继续执行。区分 desiredState（后端要求）、reportedState（EA 上报）、命令 PENDING/DELIVERED/ACKNOWLEDGED/FAILED/EXPIRED 与最后心跳。远端发送成功不等于 EA 已应用。网络失效时本地交易策略需具有可配置的 fail-closed 保护。

## 六、数据库设计基线（PostgreSQL + Prisma）

| 领域 | 目标数据表 |
| --- | --- |
| 组织与权限 | organizations、users、organization_members |
| 交易账户 | trading_accounts、account_roles、account_snapshots |
| EA | ea_definitions、ea_instances、ea_magic_bindings |
| Bridge | ea_bridge_credentials、ea_heartbeats、ea_bridge_commands |
| Broker | broker_orders、broker_deals、broker_positions、sync_cursors |
| 归属 | ea_execution_events、deal_execution_links |
| Netting | strategy_virtual_positions、virtual_position_ledger |
| 信号 | strategy_signals、copy_external_signals |
| CopyFactory | copy_strategies、copy_subscriptions、copy_sync_jobs、copy_trade_links |
| 可靠性和审计 | outbox_events、audit_logs、alert_events |

关键关系：TradingAccount 1:N EaInstance；EaDefinition 1:N EaInstance；EA 实例与 CopyStrategy 有明确关联；CopyStrategy 1:N CopySubscription；Subscriber Account 1:N CopySubscription。账户角色使用关系表，避免 EA_SOURCE/SUBSCRIBER 单值角色限制未来扩展。CopyStrategy 的本地来源账户不等于 CopyFactory 标准 Netting Provider。

关键约束：所有租户资源必须按 organizationId 隔离；Broker Deal 对 (accountId, brokerDealId) 唯一，EA 事件对 (eaInstanceId, sourceEventId) 唯一；Magic/品种和时间范围约束不得产生静默重叠；CopyFactory 外部信号 ID 必须稳定；CopyFactory 配置分别保存 desiredConfig 与 confirmedRemoteConfig 及版本。金额、数量用 PostgreSQL NUMERIC / Prisma Decimal，时间存 UTC，交易 Ticket 用无精度损失的字段。

当前仓库的 prisma/schema.prisma 是 PoC 初版，并非以上模型全部落地；生产 Schema 在 Phase 0 后冻结，后续以 Migration 演进，不直接覆盖已存在数据。

## 七、NestJS 模块与进程

- AuthModule：用户认证、租户与 RBAC。
- AccountModule：MT5 源账户及 MT4/MT5 Hedging Subscriber、资格验证。
- MetaApiModule：SDK 适配、账户查询、Broker 数据同步。
- CopySignalPoCModule：Phase 0 只读读取及成交关联预览；当前已提交基础代码。
- EaModule：EA 定义、实例、Magic 与有效时间。
- EaBridgeModule：激活、心跳、状态、命令、交易事件。
- NettingEngineModule：EA 虚拟持仓与不可变流水。
- SignalModule：信号版本、确认、重试、去重、UNKNOWN 状态。
- CopyFactoryModule：外部信号、策略与 Subscriber 的全量配置管理。
- SubscriptionModule：订阅与倍率/风控。
- ReconciliationModule：Broker、虚拟仓位、CopyFactory 和 Subscriber 四层对账。
- AuditModule / RiskModule / AlertModule / AnalyticsModule / RealtimeModule：审计、风控、告警、统计和实时前端。

长连接 MetaAPI 同步优先放在单独 Worker，连接池复用并等待同步，避免每次请求反复连接。后续多 Worker 扩容需要账户租约与 fencing。BullMQ 负责任务调度、重试和后台通知，持久化数据以 PostgreSQL 为准。

## 八、接口设计

统一前缀 /api/v1。目前已提交的 PoC 接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /health | 基础健康检查 |
| GET | /poc/accounts/:accountId | MetaAPI 账户查询 |
| POST | /poc/accounts/:accountId/attribution-preview | Magic/品种候选关联 |
| POST | /poc/accounts/:accountId/link-executions | Broker Order/Deal ID 来源核验 |

PoC 使用 x-poc-admin-key，仅限本地受控 Demo 测试，后续以正式认证、组织授权和审计替换。当前结果不跨请求持久化，不等于正式的幂等来源账本。

后续规划接口：GET/POST /accounts；GET /accounts/:id/eligibility；GET/POST /ea-instances；POST /bridge/register、/bridge/heartbeat、/bridge/events、/bridge/commands/:id/ack；GET /virtual-positions；GET/POST /copy-strategies、/copy-subscriptions；PATCH /copy-subscriptions/:id；POST /copy-subscriptions/:id/reconcile；GET /copy-sync-jobs、/alerts。

对外部信号发布及远端订阅修改返回 202 + Job ID，仅表示异步任务已接受，远端回查成功后才呈现 SYNCED。暂停新开仓、暂停新复制和紧急平仓是三个独立操作，不共用一个按钮或未经验证的 closeOnly 设置。

## 九、CopyFactory 外部信号设计原则

1. 不使用 MT5 Netting 标准 CopyFactory Provider 路线。
2. 使用稳定的外部信号 ID 对应 EA 独立逻辑仓位，变更时更新同一信号；不能每次变更新增信号。
3. 先核实 Broker 成交与 Netting 虚拟仓位，再发布外部信号，未经确认不能复制。
4. Worker 提交超时标记 UNKNOWN，并回查远端，而非直接无条件重试。
5. CopyFactory Subscriber 配置可能为包含多个订阅的整体对象，修改一个策略时必须按 Subscriber 串行更新、保留全部既有订阅并回查。
6. 需单独实测创建、加仓、部分减仓、全部平仓、反手、品种映射、最小手数、滑点、网络异常及重启恢复。
7. CopyFactory 的具体 SDK 字段以实施时的官方 API 与运行版本核查结果为准，不把尚未验证的 API 语义写成已实现。

## 十、安全、可靠性及可观测性

- MetaAPI Token、数据库密码、EA 实例凭证只在服务端，不提交 Git，不发送至 Web 客户端；公开仓库需要格外防范泄露。
- 所有接口做 DTO 验证、租户授权、速率限制和操作审计；日志敏感信息脱敏。
- Broker 原始数据不可随意修改；交易相关状态机有时间戳、版本号、幂等键和事件出处。
- 使用事务性 Outbox、幂等消费者、任务重试退避及 UNKNOWN 远端对账，禁止因超时盲目重复交易。
- 告警指标：EA 心跳过期、Broker 同步延迟、歧义来源事件、外部信号 UNKNOWN、订阅远端配置漂移、跟单执行偏差及队列积压。
- MT5 主账户交易风险由 EA 本地风控承担，不能依赖远程 WebRequest 保证资金安全。
- 实盘启用需要独立安全评审；Demo 成功不自动授权实盘执行。

## 十一、里程碑与验收标准

### Phase 0：Netting External Signals 可行性验证（当前）

准备 MT5 Netting Demo 主账户、MT4 Demo Subscriber、MT5 Hedging Demo Subscriber，以及简单可控的自研 MQ5 测试 EA。

验收清单：
- 本机 pnpm install、prisma validate、build、test 正常；
- MetaAPI 可读取实际主账户资料、Order/Deal 历史；
- EA 事件携带可核对的 Broker Order/Deal ID，拒绝重复与歧义；
- 多 EA 同品种反向交易的虚拟持仓有明确分配和可重放账本；
- CopyFactory 外部信号可在 Demo 创建、更新、关闭并回查；
- MT4 和 MT5 Hedging 都验证开仓、加仓、部分减仓、完全平仓及反手；
- 超时、重复请求、断线、Worker 重启不产生重复仓位；
- 所有测试保留事件 ID、Ticket、外部信号 ID、跟单结果和对账报告。

**任何关键场景失败，停止进入真实资金阶段。** 需记录不兼容情况并评估信号映射或其他执行方案。

### Phase 1：工程与账户基础

NestJS 模块化、Prisma 完整迁移、Auth/组织隔离、MetaAPI Worker、原始 Broker Deal 持久化。验收包含错误权限拒绝、MT4/MT5 账户识别、Worker 重启后无重复数据。

### Phase 2：EA Bridge 与 Netting 引擎

EA 凭证、心跳、暂停/恢复、交易事件、Broker 严格核验、虚拟仓位账本。验收暂停后不新开仓且继续管理原仓，Netting 同品种多 EA 场景可对账。

### Phase 3：CopyFactory 策略及订阅

策略管理、稳定外部信号、一个 Subscriber 多订阅、倍数与风控、全量配置合并、远端同步和对账。验收修改一个订阅不覆盖其他订阅，故障恢复不复制重复交易。

### Phase 4：Web 管理后台

Vue 3 / Vben Admin 实现账户、EA 实例、策略、订阅、虚拟仓位、交易明细、风控告警及统计。验收显示期望/观察/远端确认状态与新鲜度，权限和审计完整。

### Phase 5：生产准备

压测、故障演练、日志监控、TLS/密钥服务、数据库备份与恢复、风险审查、人工应急流程。上线必须经过独立批准。

## 十六、账户维护、手动交易与 WebSocket 实时功能（补充需求，2026-10-19）

本节为正式范围补充，后续开发需同时满足账户维护、人工交易、账户实时展示三类能力。它们与 EA Netting 自动跟单链路并列，但不得将用户手动交易未经授权地送入 CopyFactory 外部信号系统。**本节是方案设计，不表示相应执行代码已经实现。**

### 16.1 账户维护 AccountModule

- **账户接入**：以 MetaAPI Account ID 绑定已有 MT4/MT5 账户；读取 Broker login、server、platform、currency、positionMode、CopyFactory 资格和 MetaAPI 账户状态，并按组织隔离，绝不在前端接收 MetaAPI 主 Token。
- **账户角色**：支持 MT5 Netting 主 EA 源账户、MT4 Subscriber、MT5 Hedging Subscriber；未来一个账户可有多个业务角色，禁止仅靠单值字段限制扩展。
- **维护功能**：账户列表与详情、标签与备注、同步状态、最近一次成功同步时间、Broker 连通性、启用/禁用平台管理、重新同步、账户解绑；绑定账户之前检查是否已在本组织或其他组织绑定，重复绑定和跨租户账户授权均需有明确政策。
- **部署与连接**：区分本地账户绑定、MetaAPI 远端部署/连接状态与 CopyFactory 授权，不能将“绑定”理解为在 Broker 创建交易账户。远端账号部署和重新连接需由后台任务执行，并显示实际结果。
- **解绑保护**：存在活跃 EA、未结清手动交易请求、未结束外部信号或有效跟单订阅时，不允许直接物理删除关联记录；采取停用/软删除、依赖关系检查与审计。
- **数据展示**：余额、净值、保证金、可用保证金、货币、持仓、挂单、历史订单和成交；所有金额使用 Decimal，所有快照标明数据来源及时间。
- **故障状态**：单独跟踪账户连接、同步、数据新鲜度与错误详情；重连和同步失败必须可见，不能以旧数据假装实时状态。

建议 API：`GET/POST /api/v1/accounts`、`GET/PATCH /api/v1/accounts/:id`、`POST /api/v1/accounts/:id/sync`、`POST /api/v1/accounts/:id/disable`、`POST /api/v1/accounts/:id/unbind`、`GET /api/v1/accounts/:id/status`、`GET /api/v1/accounts/:id/snapshot`、`GET /api/v1/accounts/:id/positions`、`GET /api/v1/accounts/:id/orders`、`GET /api/v1/accounts/:id/deals`。这些是拟定 REST 路由，须实施时补 DTO 和权限约束。

**验收标准**：MT5 主账户、MT4 与 MT5 Hedging 跟单账户均可识别；无法跨组织访问；绑定/重复绑定/禁用/解绑及依赖拦截均可测试；Worker 重启后能恢复账户同步，历史数据不重复，错误和数据时效正确显示。

### 16.2 独立的手动交易 TradeModule

手动交易是一条**独立于 EA Bridge、Netting Signal Engine 和 CopyFactory 自动跟单**的业务通道：

`Web/授权用户 → NestJS TradeModule → 持久化 TradeRequest → MetaAPI RPC → Broker 回查与对账 → 数据库/WebSocket`

首期规划：手动市价买入/卖出、允许的挂单类型、撤销挂单、修改止损止盈、全平与部分平仓，以及订单状态查询。每种交易操作都必须确认 MT4/MT5 平台和 Broker 支持的指令语义，实际 RPC SDK 方法与参数需在实现时核对。

**特别处理 MT5 Netting 主 EA 账户：** 人工交易可能改变 EA 的共享净持仓，影响 EA 虚拟持仓及 CopyFactory 信号。默认禁止直接对承载 EA 的 Netting 主账户使用人工开仓、减仓、反手或其他会改变仓位的指令；如未来允许，必须实现账户级交易锁、风险确认、EA/账本同步、归属策略和审计，且不把手动交易隐式归到任何 EA。对 Subscriber 人工改仓也要标记为跟单偏离，避免后续信号错误覆盖。

交易请求状态建议：`PENDING → VALIDATED → SUBMITTED → CONFIRMED/REJECTED`，提交超时必须进入 `UNKNOWN`，先按 Broker Ticket/请求标识对账，不可盲目重试。客户端的 `Idempotency-Key` 和数据库唯一约束只能防止平台重复请求，并**不等于 Broker 层的原子幂等保证**。异步操作返回 `202 + requestId`，只代表受理；确认执行必须由 Broker 事实决定。关键操作需二次确认、风险参数检查、角色授权和不可修改的审计记录。

建议 API：`POST /api/v1/trade-requests/market-order`、`POST /api/v1/trade-requests/pending-order`、`POST /api/v1/trade-requests/close-position`、`POST /api/v1/trade-requests/modify-protection`、`POST /api/v1/trade-requests/cancel-order`、`GET /api/v1/trade-requests/:id`。全部仅为待实现设计，**当前不得作为已开放下单端点使用**。

数据表补充：`trade_requests`（租户/账户/操作者/幂等键/动作/请求参数/状态/错误及时间）、`trade_request_attempts`（提交尝试与 RPC 结果）、`trade_execution_links`（Broker Order/Deal 回执关联）、`manual_trade_audit`（或统一 audit_logs）。请求和反馈禁止保存明文交易凭证。

**验收标准**：Demo 下单、改单、撤单、全平/部分平仓有 Broker 实际回查；重试、并发重复、超时未知状态不导致多次订单；不同组织绝无越权；承载 EA 的 Netting 源账户默认阻止可能破坏 EA 虚拟仓位的人工交易；未经明确用户授权不会触发 CopyFactory 跟单。

### 16.3 WebSocket 实时通信 RealtimeModule

WebSocket 用于**状态推送，而不是交易事实来源**。Broker 事件先确认并写入数据库，再向已鉴权的前端推送轻量通知。前端首次连接或重连先通过 REST 获取可验证快照，再消费增量事件；断线期间的数据必须可通过版本/游标补拉，不能依赖 WebSocket 消息单独重建持仓或资金数据。

事件主题建议：

| 事件 | 数据 |
| --- | --- |
| `account.status.changed` | 连接、同步、最后更新时间 |
| `account.snapshot.updated` | 余额、净值等快照更新通知 |
| `broker.position.changed` | 仓位变化及对应数据版本 |
| `broker.order.changed` | 订单与挂单状态 |
| `broker.deal.created` | 新成交的只读摘要 |
| `ea.heartbeat.changed` | EA 心跳与运行状态 |
| `ea.command.status` | EA 控制回执 |
| `signal.status.changed` | Netting 信号状态 |
| `copy.subscription.changed` | 订阅配置及生效状态 |
| `copy.reconciliation.alert` | 对账漂移或异常 |
| `trade.request.status` | 手动交易受理/提交/确认/拒绝/未知 |

安全设计：握手鉴权与过期令牌处理、按组织和账户授权分房间、订阅前验证所属关系，禁止客户端自己选择任意组织房间；针对高频净值/持仓更新做节流和聚合；重要事件使用 Outbox + Worker 推送以减少数据库已提交但消息丢失的问题。可采用 Socket.IO 与 NestJS Gateway，正式部署时评估 Redis Adapter 处理多实例广播。

推荐统一事件信封：`{ eventId, type, organizationId, resourceId, version, occurredAt, payload }`；不推送密钥和不必要的敏感信息。前端使用 `version` 或游标去重、乱序保护和断线补拉；在线状态要标明 `asOf`，超时显示 `STALE`。

**验收标准**：同时打开两个浏览器连接后，相同组织的授权资源有正常同步；跨组织房间订阅失败；断线重连自动恢复快照并补齐关键变化；重复/乱序消息不会让页面倒退；WebSocket 断开不影响 Broker 同步或后台下单状态机。

### 16.4 开发排期调整

- **Phase 0 不变**：优先验证 MetaAPI 账户读取、Broker Deal 关联、Netting 虚拟仓位与 CopyFactory External Signals Demo 复制，避免关键技术路线返工。
- **Phase 1 扩展**：实现 AccountModule 的完整账户维护、Broker 状态/快照/持仓/订单/成交查询、组织授权及持久化对账。
- **Phase 2 并行基础设施**：EA Bridge/Netting 引擎之外，建设 RealtimeModule 的权限隔离、事件信封、快照+增量机制；前端可在 Phase 4 接入。
- **Phase 3 扩展**：实现订阅管理与 TradeModule 的受控 Demo 手动交易能力，先对 Subscriber 或单独 Demo 非 EA 账户测试，**不得默认允许直接干预 Netting 源账户**。
- **Phase 4 扩展**：Web 后台增加账户维护、实时状态、持仓和订单页面、手动交易面板、请求执行跟踪及风险提示。
- **Phase 5**：手动交易权限、限额、二次确认、紧急操作与 WebSocket 断线演练列为生产前强制验收。

### 16.5 业务优先级与防误用约束

账户查询和维护属于 P1；WebSocket 实时状态基础属于 P1/P2；手动交易执行属于 P2/P3 且**仅在 Demo 安全验证后开放**。生产环境需独立控制 `manualTradingEnabled` 和可交易账户白名单，默认关闭。无论自动或手动流程，禁止将“API 接受请求”直接标记为“Broker 已成交”。

### 17.2 Server 下拉搜索交互与数据流程

前端“添加交易账户”表单：
1. 先选择 `MT4` 或 `MT5`。
2. 输入 Broker 名称或 Server 关键词，输入停止约 300–500ms 后请求后端；输入为空时不发起广域查询。
3. NestJS 代理向 MetaAPI Provisioning API 检索服务器，不向浏览器暴露 MetaAPI Token。
4. UI 以 Broker 分组展示 Server，保留 Server 原始名称，不自行拼接或改写。
5. 搜索无结果/MetaAPI 不可达时，用户可以手动填写服务器名称；提示尚未验证。
6. 绑定 MetaAPI 账户后从实际 accountInformation 校验 platform/server/login/broker，并展示连接/同步状态。
7. 搜索结果可短期缓存，注明搜索时间和来源；选择结果并不意味着账号密码有效或 Broker 一定可连接。

规划 API：
- `GET /api/v1/brokers/servers?platform=MT5&query=ICMarkets`
- `POST /api/v1/accounts`（创建/绑定账户，具体认证信息以账户接入流程定义）
- `GET /api/v1/accounts/:id/status`
- `POST /api/v1/accounts/:id/verify`

安全：对关键字长度、请求频率、查询超时和供应商限流进行控制；不要记录明文交易密码；MetaAPI 管理 Token 后端保管。接口若需不同区域或 SDK 不提供封装，则通过专用 HTTP Adapter 使用官方 URL 和服务端令牌，避免写死在前端。

### 17.3 账户品种目录与平台启用/默认品种

**不能把 Server 与品种定义成一对一关系。** 同一 Broker Server 的账户可能因账户组、权限、品种后缀、账户类型而获得不同符号与交易规格。以 **accountId + brokerSymbol** 作为实际目录边界。

建议增加数据表：

| 表 | 字段与用途 |
| --- | --- |
| `account_symbols` | `id`, `accountId`, `brokerSymbol`, `displayName`, `specification Json`, `brokerVisible`, `tradeAllowedObserved`, `lastSeenAt`, `specificationUpdatedAt`, `isEnabled`, `isDefault` |
| `canonical_instruments`（后期） | 归一化产品定义，如 `XAUUSD`、`EURUSD`；不替代 Broker 原始 Symbol |
| `account_symbol_mappings`（后期） | 不同账户原始品种映射，如 `XAUUSD` → `XAUUSDm`；用于 CopyFactory 跟单与跨账户展示 |

数据库约束：`@@unique([accountId, brokerSymbol])`；对每账户至多一个默认品种使用 PostgreSQL 部分唯一索引或单独 `trading_accounts.defaultSymbolId` 外键；默认必须属于本账户且平台已启用。账户删除/停用时维护关联完整性。

**三区分原则：**
- `brokerVisible / tradeAllowedObserved`：MetaAPI/Broker 实际观测到的能力；
- `isEnabled`：本平台管理员选择允许展示/监控/通过手动交易入口使用；
- `isDefault`：用户打开这个账户时的默认行情、图表和交易面板品种。

后两者是本平台设置，**不修改 Broker 实际可交易品种权限**。账户品种一旦被 Broker 移除或规格变化，应保留原记录及最后观测时间以供历史订单引用，同时禁止新的手动下单或跟单映射，不能把本地 `isEnabled=true` 当作 Broker 放行依据。

管理 API：
- `GET /api/v1/accounts/:id/symbols?enabled=true|false`
- `POST /api/v1/accounts/:id/symbols/sync`
- `GET /api/v1/accounts/:id/symbols/:symbol/specification`
- `PATCH /api/v1/accounts/:id/symbols/:symbol`（平台启用/停用）
- `PUT /api/v1/accounts/:id/default-symbol`（设置账户默认品种）
- `GET /api/v1/instruments/mappings`、`PUT /api/v1/instruments/mappings`（后期）

接口中的 `:symbol` 必须 URL 编码并按服务端路径路由要求处理，不能假设品种名只包含大写字母。

### 17.4 品种同步和交易检查

- 账户首次达到可同步状态后拉取 symbols，按需或批量读取规格；周期性刷新并支持用户手动刷新，不对每次页面请求调用供应商 API。
- 最好使用带时间戳的缓存和数据库快照，订阅 MetaAPI 的相关更新事件作为失效线索；规范无法保证所有规格变化实时推送时，必须周期性回查。
- 同步过程采用差异更新：新增品种录入；规格变化更新版本/时间；已消失品种标为当前不可见但历史不删。
- 后台提供按账户筛选、搜索品种、启用/停用开关、设置唯一默认品种；默认列表只展示启用且 Broker 仍可用的品种。
- 手动下单时在实际发送 RPC 前重新校验 Broker 连接、交易权限、价格新鲜度、品种可用、最小/最大 Volume、Volume Step、止损距离、交易时间以及账户风控，不得仅依据缓存或 UI 状态。
- 跟单时维持源策略品种与 Subscriber Broker 品种的显式映射，不能默认为两端品种名称相同；缺少映射时阻止该订阅信号进入发送流程并告警。

### 17.5 MetaAPI 仍需专项确认的功能

下列能力需要在实施阶段依官方 API/SDK 与 Demo 验证，不应将它们写成既有实现：

1. 账户 Provisioning：创建或接管 API 账户、部署、等待连接、禁用/解绑、账户地区及账户资源限制；“绑定 MetaAPI ID”与“新建 Broker 交易账户”必须区分。
2. 账户数据：balance/equity/margin、持仓/订单/成交/历史；MT4 Order 与 MT5 Order/Deal/Position 的差异；Netting/Hedging 模式及 tradeAllowed。
3. 品种与行情：getSymbols、Symbol Specification、实时报价、Candles/Ticks、市场休市和报价过期判断；行情订阅数与调用限额。
4. 手动交易：开仓、挂单、改单、撤单、部分平仓、反手、请求超时 UNKNOWN、Broker 结果回查和禁止误操作 EA Netting 源账户。
5. WebSocket/Streaming：连接重用、同步完成、断线重连、事件顺序、推送新鲜度以及前端 Snapshot + Incremental 机制。
6. CopyFactory：外部信号版本、稳定 ID、生命周期、Subscribe 全量更新语义、MT4/MT5 Hedging 差异、品种映射、CopyFactory 风控、执行回查。
7. API 配额、供应商计费、区域延迟、历史数据时间范围、断线和账号凭证变更流程。
8. 可选增强：历史 K 线和市场数据缓存、账户风险指标与 MetaStats 的评估；只有确认实际价值后增加第三方依赖。

### 17.6 开发优先级与验收

- **Phase 0（当前）：** 优先保留 MT5 Netting → Broker Deal → EA 策略来源关联与 CopyFactory External Signals Demo 可行性验证；同时为 Broker Server 搜索与账户 Symbols 读取建立独立 PoC。
- **Phase 1（账户维护）：** 完成 Broker/Server 搜索下拉、手动 Server 兜底、账户验证、Symbols/Specification 同步、平台启用开关、单账户默认品种与数据新鲜度。
- **Phase 2（交易/跟单）：** 接入账户品种资格、跨账户品种映射及下单前规格验证，确保 MT4/MT5 Subscriber 按各自 Broker 规则执行。

**验收用例：**
1. MT4 与 MT5 Server 搜索独立，按 Broker 分组，输入关键字返回可选结果，无结果仍可手动输入。
2. 不同 Server 的账户返回不同 Broker Symbol 时，分别展示并独立持久化，互不污染。
3. 同一 Server 下不同账号的品种权限及规格也按账号独立记录。
4. 可开启/关闭本平台可用的账户品种，可设置恰好一个或零个默认品种（未配置允许为空）；禁用品种不能成为默认。
5. Broker 移除/禁用品种后，后台保留历史记录但停止该品种新的手动交易/跟单操作并显示数据时效。
6. XAUUSD 与 XAUUSDm 不会自动误匹配；映射必须显式确认。
7. MetaAPI 查询超时/不可达时保留旧数据并标记 STALE，不假装是实时结果。
8. 不暴露 MetaAPI Token 或账户交易凭证，跨组织无法查询 Server 账户绑定信息或账户品种。
